预打包操作是可直接使用的工作流任务，可帮助你自动化常见任务，例如构建、提交和测试应用程序。它们提供了一种标准化的方式来处理这些操作，而无需从头编写自定义任务配置。本指南将介绍可用的预打包操作以及如何在工作流中使用它们。

## 构建

将你的项目构建为 Android 或 iOS 应用。

构建作业可以自定义，因此你可以在构建过程中执行自定义命令。更多信息请参见 [自定义构建](/custom-builds/get-started/)。

<Prerequisites>
  <Requirement title="EAS Build 的项目配置">
    你的项目必须已为 EAS Build 完成设置：**eas.json** 必须包含作业使用的构建配置文件，并且必须为该平台配置应用签名凭据。你可以先运行构建而不执行它，通过运行 `eas credentials:configure-build -p <platform> -e
    <profile>`，使用与作业相同的平台和配置文件来设置凭据。了解更多关于 [为 EAS Build 配置你的项目](/build/setup/) 的信息。
  </Requirement>
</Prerequisites>

### 语法

```yaml
jobs:
  build_app:
    type: build
    runs_on: string # 可选 - 可用选项请参见 https://docs.expo.dev/build-reference/infrastructure/
    params:
      platform: android | ios # 必需
      profile: string # 可选 - 默认值：production
      message: string # 可选
      refresh_ad_hoc_provisioning_profile: boolean # 可选
    hooks:
      before_install_node_modules: step[] # 可选 - 在构建安装依赖项之前运行的步骤。
      after_install_node_modules: step[] # 可选 - 在构建安装依赖项之后运行的步骤。
```

#### 参数

你可以向 `params` 列表传入以下参数：

| 参数                                | 类型  | 描述                                                                                                                                                                                                                                                                                                   |
| ----------------------------------- | ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| platform                            | string  | **必需。** 要构建的平台。可以是 `android` 或 `ios`。                                                                                                                                                                                                                                                    |
| profile                             | string  | 可选。要使用的构建配置文件。默认值为 `production`。                                                                                                                                                                                                                                                     |
| message                             | string  | 可选。附加到构建上的自定义消息。对应运行 `eas build` 时的 `--message` 标志。                                                                                                                                                                                                                          |
| refresh_ad_hoc_provisioning_profile | boolean | 可选。在 iOS 内部分发构建开始前刷新受管理的 ad hoc 配置文件。对应运行 `eas build` 时的 [`--refresh-ad-hoc-provisioning-profile`](/eas/cli/#eas-build) 标志。参见 [CI 上的内部分发](/build/internal-distribution/#automation-on-ci-optional)。 |

#### 环境变量

如果你在构建过程中需要某些环境变量，可以将它们包含在你指定构建 `profile` 的 [eas.json](/eas/json/#environment) 中。它们将从 [EAS 环境变量](/eas/environment-variables/) 中提取。

#### 输出

你可以在后续作业中引用以下输出：

| 输出              | 类型   | 描述                                                      |
| ----------------- | ------ | --------------------------------------------------------- |
| build_id          | string | 创建的构建的 ID。                                         |
| app_build_version | string | 应用的版本代码/构建号。                                   |
| app_identifier    | string | 应用的包标识符/包名。                                     |
| app_version       | string | 应用的版本。                                              |
| channel           | string | 构建所使用的更新通道。                                    |
| distribution      | string | 使用的分发方式。可以是 `internal` 或 `store`。            |
| fingerprint_hash  | string | 构建的指纹哈希。                                          |
| git_commit_hash   | string | 构建所使用的 git 提交哈希。                               |
| platform          | string | 创建构建所对应的平台。为 `android` 或 `ios`。            |
| profile           | string | 使用的构建配置文件。                                      |
| runtime_version   | string | 使用的运行时版本。                                        |
| sdk_version       | string | 使用的 SDK 版本。                                         |
| simulator         | string | 是否为模拟器构建。                                        |

#### 钩子

构建作业支持以下钩子：

- `before_install_node_modules`：在构建安装项目依赖项之前运行的步骤。
- `after_install_node_modules`：在构建安装项目依赖项之后运行的步骤。

关于通用钩子语法，请参见 [`jobs.<job_id>.hooks`](/eas/workflows/syntax/#jobsjob_idhooks)。

### 示例

以下是一些使用构建作业的实用示例：

<Collapsible summary="针对特定平台的基础构建">

```yaml .eas/workflows/build-ios.yml
  push:
    branches: ['main']

  build_ios:
    name: Build iOS
    type: build
    params:
      platform: ios
      profile: production
```

</Collapsible>

<Collapsible summary="同时为两个平台构建">

此工作流会在你推送到 main 分支时并行构建 Android 和 iOS 应用。

```yaml .eas/workflows/build-all.yml
name: Build for all platforms

on:
  push:
    branches: ['main']

jobs:
  build_android:
    name: Build Android
    type: build
    params:
      platform: android
      profile: production

  build_ios:
    name: Build iOS
    type: build
    params:
      platform: ios
      profile: production
```

</Collapsible>

<Collapsible summary="使用环境变量构建">

此工作流会使用可在构建过程中使用的自定义环境变量来构建你的 Android 应用。

```yaml .eas/workflows/build-with-env.yml
name: 使用环境变量构建

on:
  push:
    branches: ['main']

  build_android:
    name: Build Android
    type: build
    env:
      APP_ENV: production

```

</Collapsible>

<Collapsible summary="使用不同配置文件构建">

此工作流使用不同配置文件创建两个不同的 Android 构建——一个用于内部分发，另一个用于提交到商店，分别使用 development 和 production 配置文件。

```yaml .eas/workflows/build-profiles.yml

  push:
    branches: ['main']

jobs:
  build_android_development:
    name: Build Android Development
    type: build
    params:
      platform: android
      profile: development

  build_android_production:
    name: Build Android Production
    type: build
    params:
      platform: android
      profile: production
```

</Collapsible>

<Collapsible summary="使用刷新的 ad hoc 配置文件进行 iOS 内部构建">

此工作流会为你的 iOS 应用进行内部分发构建，并在你推送到 main 分支时刷新 ad hoc 配置文件。

```yaml .eas/workflows/build-ios-internal.yml
name: Build iOS internal

on:
  push:
    branches: ['main']

jobs:
  build_ios:
    name: Build iOS Internal
    type: build
    params:
      platform: ios
      profile: preview
      refresh_ad_hoc_provisioning_profile: true
```

</Collapsible>

## 部署

使用 [EAS Hosting](/eas/hosting/introduction) 部署你的应用程序。

<Prerequisites>
  <Requirement title="已配置 EAS Hosting 的项目">
    请参阅 [开始使用 EAS Hosting](/eas/hosting/get-started/#prerequisites) 以获取设置说明。
  </Requirement>
</Prerequisites>

### 语法

```yaml
jobs:
  deploy_web:
    type: deploy
    params:
      alias: string # optional
      prod: boolean # optional
      source_maps: boolean # optional
    hooks:
      after_checkout: step[] # optional - steps to run after the job checks out your project.
      before_install_node_modules: step[] # optional - steps to run before the job installs dependencies.
      after_install_node_modules: step[] # optional - steps to run after the job installs dependencies.
```

#### 参数

你可以向 `params` 列表传入以下参数：

| 参数        | 类型    | 描述                                                                        |
| ----------- | ------- | --------------------------------------------------------------------------- |
| alias       | string  | 可选。要部署到的 [别名](/eas/hosting/deployments-and-aliases/#aliases)。   |
| prod        | boolean | 可选。是否部署到生产环境。                                                   |
| source_maps | boolean | 可选。是否随部署一起上传 source maps。                                       |

#### 输出

你可以在后续作业中引用以下输出：

| 输出                  | 类型   | 描述                                                                                                                                      |
| --------------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| deploy_json           | string | 包含部署详情的 JSON 对象（`npx eas-cli deploy --json` 的输出）。                                                                          |
| deploy_url            | string | 指向该部署的 URL。如果这是一个生产部署，则使用生产 URL。否则，使用第一个别名 URL 或部署 URL。                                            |
| deploy_alias_url      | string | 指向该部署的别名 URL（例如，`https://account-project--alias.expo.app`）。                                                                |
| deploy_deployment_url | string | 指向该部署的唯一 URL（例如，`https://account-project--uniqueid.expo.app`）。                                                              |
| deploy_identifier     | string | 部署的标识符。                                                                                                                             |
| deploy_dashboard_url  | string | 指向部署仪表板的 URL（例如，`https://expo.dev/projects/[project]/hosting/deployments`）。                                                |

#### Hooks

Deploy 作业支持以下 hooks：

- `after_checkout`：作业检出项目后要运行的步骤。
- `before_install_node_modules`：作业安装项目依赖项之前要运行的步骤。
- `after_install_node_modules`：作业安装项目依赖项之后要运行的步骤。

有关通用 hooks 语法，请参阅 [`jobs.<job_id>.hooks`](/eas/workflows/syntax/#jobsjob_idhooks)。

### 示例

以下是一些使用部署作业的实用示例：

<Collapsible summary="部署到生产环境的基础示例">

此工作流会使用 EAS Hosting 将你的应用程序部署到生产环境。

```yaml .eas/workflows/deploy-basic.yml
name: Basic Deployment

jobs:
  deploy:
    name: Deploy to Production
    type: deploy
    params:
      prod: true
```

</Collapsible>

<Collapsible summary="仅在合并到 `main` 分支时部署到生产环境">

此工作流会在你合并到 main 分支时将应用程序部署到生产环境，并在所有其他分支上进行非生产环境部署。

```yaml .eas/workflows/deploy.yml
name: Deploy

on:
  push:
    branches: ['*']

jobs:
  deploy:
    name: Deploy
    type: deploy
    params:
      prod: ${{ github.ref_name == 'main' }}
```

</Collapsible>

<Collapsible summary="使用自定义别名进行部署">

此工作流会将你的应用程序部署到生产环境中的一个自定义别名。

```yaml .eas/workflows/deploy-alias.yml
name: Deployment with Alias

jobs:
  deploy:
    name: Deploy with Alias
    type: deploy
    params:
      alias: my-custom-alias
      prod: true
```

</Collapsible>

## 指纹

计算你的项目指纹。

> **注意：** 此作业类型仅支持 [CNG](/workflow/continuous-native-generation/) 工作流。如果你提交了 **android** 或 **ios** 目录，指纹作业将无法工作。

> **注意：** 为确保指纹与你的构建匹配，请使用与构建配置文件相同的 `environment` 设置。对于环境变量，我们建议使用 [EAS 环境变量](/eas/environment-variables/) 而不是 [`env`](/eas/workflows/syntax/#jobsjob_idenv) 字段，以获得更好的一致性。

### 语法

```yaml
jobs:
  fingerprint:
    type: fingerprint
    environment: production | preview | development # 可选，默认值为 production
    env: # 可选的环境变量列表
      ENV_VAR_NAME: value
    hooks:
      after_checkout: step[] # 可选 - 作业检出项目后运行的步骤。
      before_install_node_modules: step[] # 可选 - 作业安装依赖项前运行的步骤。
      after_install_node_modules: step[] # 可选 - 作业安装依赖项后运行的步骤。
```

#### 环境变量

你可以向 `env` 参数传入一个环境变量列表。这些环境变量将从 [EAS 环境变量](/eas/environment-variables/) 中提取。传入的 `environment` 参数将用于该环境变量所属的环境，当同一个环境变量在不同环境中都被定义时，这会很有用。

#### 参数

你可以向 `params` 列表传入以下参数：

| 参数                    | 类型    | 描述                                                                                                  |
| ----------------------- | ------- | ----------------------------------------------------------------------------------------------------- |
| unstable_skip_cng_check | boolean | 可选。是否跳过 [Continuous Native Generation (CNG)](/workflow/continuous-native-generation/) 兼容性检查。默认值为 `false`。 |

#### 输出

你可以在后续作业中引用以下输出：

| 输出                     | 类型   | 描述                       |
| ------------------------ | ------ | -------------------------- |
| android_fingerprint_hash | string | Android 的指纹哈希。       |
| ios_fingerprint_hash     | string | iOS 的指纹哈希。           |

#### Hooks

指纹作业支持以下 hooks：

- `after_checkout`：作业检出项目后运行的步骤。
- `before_install_node_modules`：作业安装项目依赖项前运行的步骤。
- `after_install_node_modules`：作业安装项目依赖项后运行的步骤。

有关通用 hooks 语法，请参阅 [`jobs.<job_id>.hooks`](/eas/workflows/syntax/#jobsjob_idhooks)。

### 示例

以下是一些使用指纹作业的实用示例：

<Collapsible summary="基础指纹计算">

此工作流会为 Android 和 iOS 构建都计算指纹。`environment` 应与构建配置文件匹配，以实现准确的指纹匹配。

```yaml .eas/workflows/fingerprint-basic.yml
name: 基础指纹

jobs:
  fingerprint:
    name: 计算指纹
    type: fingerprint
    # @info 将你的构建配置文件的 environment 匹配起来 #
    environment: production
    # @end #
```

</Collapsible>

<Collapsible summary="使用内联环境变量的指纹">

> **注意：** 如果你依赖内联环境变量，你需要始终确保在每个位置（构建配置文件、指纹作业、更新作业等）将正确的一组环境变量设置为正确的值，以确保指纹匹配。**我们建议改用 [EAS 环境变量](/eas/environment-variables/)，** 在那里你可以将变量集合分组到环境中，并在构建配置文件和工作流作业中引用它们。

```yaml .eas/workflows/fingerprint-with-env.yml
name: 使用环境变量的指纹

jobs:
  fingerprint:
    name: 计算指纹
    type: fingerprint
    environment: production
    # 结果环境将是 "production" 环境与内联环境变量的并集。
    # `env` 变量会覆盖 "production" 环境中同名的环境变量。
    env:
      APP_VARIANT: staging
      API_URL: https://api.staging.example.com
```

</Collapsible>

## 获取构建

从 EAS 中检索一个与提供参数匹配的现有构建。

### 语法

```yaml
jobs:
  get_build:
    type: get-build
    params:
      platform: ios | android # 可选
      profile: string # 可选
      distribution: store | internal | simulator # 可选
      channel: string # 可选
      app_identifier: string # 可选
      app_build_version: string # 可选
      app_version: string # 可选
      git_commit_hash: string # 可选
      fingerprint_hash: string # 可选
      sdk_version: string # 可选
      runtime_version: string # 可选
      simulator: boolean # 可选
      wait_for_in_progress: boolean # 可选
```

#### 参数

你可以将以下参数传入 `params` 列表：

| 参数                 | 类型    | 描述                                                                           |
| -------------------- | ------- | ------------------------------------------------------------------------------ |
| platform             | string  | 可选。要获取构建的平台。可以是 `ios` 或 `android`。                              |
| profile              | string  | 可选。要使用的构建配置文件。                                                     |
| distribution         | string  | 可选。发布方式。可以是 `store`、`internal` 或 `simulator`。                      |
| channel              | string  | 可选。更新通道。                                                                 |
| app_identifier       | string  | 可选。包标识符/包名。                                                            |
| app_build_version    | string  | 可选。构建版本。                                                                 |
| app_version          | string  | 可选。应用版本。                                                                 |
| git_commit_hash      | string  | 可选。git 提交哈希。                                                            |
| fingerprint_hash     | string  | 可选。指纹哈希。                                                                 |
| sdk_version          | string  | 可选。SDK 版本。                                                                 |
| runtime_version      | string  | 可选。运行时版本。                                                               |
| simulator            | boolean | 可选。是否获取模拟器构建。                                                       |
| wait_for_in_progress | boolean | 可选。是否等待匹配的进行中构建。默认：`false`。                                   |

如果将 `wait_for_in_progress` 设置为 `true`，该任务仍会优先立即继续使用一个成功的构建，但它也会查找进行中的构建。如果未找到成功的构建，任务将在继续之前等待一个进行中的构建完成。如果匹配的构建成功，任务将被标记为成功，并返回该成功构建。如果匹配的构建失败，任务仍将被标记为成功，但其输出将为空——就像没有匹配到构建一样。

#### 输出

你可以在后续任务中引用以下输出：

| 输出               | 类型   | 描述                               |
| ------------------ | ------ | ---------------------------------- |
| build_id           | string | 检索到的构建 ID。                  |
| app_build_version  | string | 应用的构建版本。                   |
| app_identifier     | string | 应用的包标识符/包名。              |
| app_version        | string | 应用版本。                         |
| channel            | string | 构建所使用的更新通道。             |
| distribution       | string | 所使用的发布方式。                 |
| fingerprint_hash   | string | 构建的指纹哈希。                   |
| git_commit_hash    | string | 构建所使用的 git 提交哈希。        |
| platform           | string | 构建创建所针对的平台。             |
| profile            | string | 所使用的构建配置文件。             |
| runtime_version    | string | 所使用的运行时版本。               |
| sdk_version        | string | 所使用的 SDK 版本。                |
| simulator          | string | 是否为模拟器构建。                 |

### 示例

以下是一些使用 get-build 任务的实际示例：

<Collapsible summary="获取最新生产构建">

此工作流从 store 发布通道中检索 iOS 的最新生产构建。

```yaml .eas/workflows/get-build-production.yml
name: 获取生产构建

jobs:
  get_build:
    name: 获取最新生产构建
    type: get-build
    params:
      platform: ios
      profile: production
      distribution: store
      channel: production
```

</Collapsible>

<Collapsible summary="按版本获取构建">

此工作流根据应用版本和构建版本检索 Android 构建的特定版本。

```yaml .eas/workflows/get-build-version.yml
name: 按版本获取构建

jobs:
  get_build:
    name: 获取特定版本构建
    type: get-build
    params:
      platform: android
      app_identifier: com.example.app
      app_version: 1.0.0
      app_build_version: 42
```

</Collapsible>

<Collapsible summary="获取模拟器构建">

此工作流为 iOS 开发检索一个模拟器构建。`wait_for_in_progress` 设置为 `true`，因此如果已经存在与过滤条件匹配的构建，任务将在继续之前等待其完成。

```yaml .eas/workflows/get-build-simulator.yml
name: 获取模拟器构建

jobs:
  get_build:
    name: 获取模拟器构建
    type: get-build
    params:
      platform: ios
      simulator: true
      profile: development
      wait_for_in_progress: true
```

</Collapsible>

## 提交

使用 EAS Submit 将 Android 或 iOS 构建提交到应用商店。

<Prerequisites>
  <Requirement title="CI/CD 提交配置">
    提交任务需要额外配置，才能在 CI/CD 流程中运行。有关更多信息，请参阅 [Google
    Play 商店 CI/CD 提交指南](/submit/android/#automate-with-eas-workflows) 和 [Apple App
    Store CI/CD 提交指南](/submit/ios/#automate-with-eas-workflows)。
  </Requirement>
</Prerequisites>

### 语法

```yaml
jobs:
  submit_to_store:
    type: submit
    params:
      build_id: string # 必填
      profile: string # 可选 - 默认值：production
      groups: string[] # 可选
    hooks:
      after_checkout: step[] # 可选 - 作业检出项目后要运行的步骤。
      before_install_node_modules: step[] # 可选 - 作业安装依赖项之前要运行的步骤。
      after_install_node_modules: step[] # 可选 - 作业安装依赖项之后要运行的步骤。
      before_submit: step[] # 可选 - 提交开始前要运行的步骤。
      after_submit: step[] # 可选 - 提交完成后要运行的步骤。
```

#### 参数

你可以将以下参数传入 `params` 列表：

| 参数 | 类型     | 描述                                                                                                                                     |
| ---- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| build_id  | string | 必填。要提交的构建 ID。                                                                                                                       |
| profile   | string | 可选。要使用的提交配置文件。默认值为 `production`。                                                                                          |
| groups    | string[] | 可选。要将构建添加到的 TestFlight 内部组名称。有关更多 TestFlight 分发选项，请参见 [TestFlight 任务](#testflight)。 |

#### 输出

你可以在后续任务中引用以下输出：

| 输出                  | 类型   | 描述                                |

## TestFlight

将 iOS 构建分发到 [TestFlight](/submit/testflight/) 内部和外部测试组。当你需要更高级的 TestFlight 功能时，可以使用此任务作为 iOS submit 任务的替代方案。如果你需要控制测试组、更新日志或 Beta App Review 提交，请使用 `testflight` 任务，而不是 submit。

该任务支持两种方式：上传一个构建并将其提交到 TestFlight（`build_id`），或提交一个已经上传的构建（`asc_build_id`）。在这两种情况下，你都可以将构建添加到分组、设置“要测试的内容”说明，并提交 Beta App Review。请且仅提供 `build_id` 或 `asc_build_id` 其中之一。

<Prerequisites>
  <Requirement title="面向外部分发的 TestFlight 测试信息">
    当分发到外部组或提交 Beta App Review（`external_groups` 和/或
    `submit_beta_review: true`）时，构建必须先在 App Store Connect 中完成所需的 TestFlight 测试信息，
    作业才可能成功。请参阅 Apple 文档中的 [提供测试信息](https://developer.apple.com/help/app-store-connect/test-a-beta-version/provide-test-information/)。
  </Requirement>
</Prerequisites>

### 共享参数

两种方式都在 `params` 中接受以下参数：

| 参数               | 类型     | 描述                                                                                                                                                                                                                                                             |
| ------------------ | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| internal_groups    | string[] | 可选。要将构建添加到的 TestFlight 内部组名称数组。仅包含未启用自动分发的组。                                                                                                                                                                                          |
| external_groups    | string[] | 可选。要将构建添加到的 TestFlight 外部组名称数组。                                                                                                                                                                                                                      |
| changelog          | string   | 可选。TestFlight 测试者的测试说明（“要测试的内容”）。                                                                                                                                                                                                                  |
| submit_beta_review | boolean  | 可选。是否提交 Beta App Review。若未指定，当提供 `external_groups` 时默认为 `true`，否则默认为 `false`。若要在不重新提交 Beta App Review 的情况下，更新已提交构建的更新日志或分组，请设为 `false`。 |

### 提交已上传的构建

将已存在于 App Store Connect 中的构建提交到 TestFlight 组，设置“要测试的内容”说明，并提交进行 Beta App Review。Beta App Review 提交是可选的。将 `submit_beta_review: false` 设为不重新提交审核，即可在现有构建上更新更新日志或分组。

<Prerequisites>
  <Requirement title="App Store Connect 集成">
    在 [项目设置 > 常规 >
    连接](https://expo.dev/accounts/[account]/projects/[project]/settings) 中配置你的 App Store Connect 连接。构建必须
    已经存在于 App Store Connect 中，并且已准备好提交。
  </Requirement>
</Prerequisites>

#### 语法

```yaml
jobs:
  testflight_distribution:
    type: testflight
    params:
      asc_build_id: string # 必需
      internal_groups: string[]
      external_groups: string[]
      changelog: string
      submit_beta_review: boolean
```

#### 参数

| 参数         | 类型   | 描述                                      |
| ------------ | ------ | ----------------------------------------- |
| asc_build_id | string | 必需。已存在于 App Store Connect 中的构建 ID。 |

你也可以传入任意 [共享参数](#shared-parameters)。

#### 输出

你可以在后续工作流中引用以下输出：

| 输出                 | 类型   | 描述                             |
| -------------------- | ------ | -------------------------------- |
| asc_build_id         | string | App Store Connect 构建 ID。       |
| apple_app_id         | string | 所提交构建的 Apple App ID。       |
| ios_bundle_identifier | string | 所提交构建的 iOS Bundle 标识符。 |

#### 示例

<Collapsible summary="在 App Store Connect 上传后自动分发到 TestFlight">

当构建上传到 App Store Connect 后，此工作流会自动将构建添加到 TestFlight 组，设置“要测试的内容”说明，并提交进行 Beta App Review。使用此触发器前请先配置你的 App Store Connect 连接。参见 [从 App Store Connect 事件触发工作流](/eas/workflows/get-started/#trigger-workflows-from-app-store-connect-events)。

`${{ app_store_connect.build_upload.build.id }}` 仅在工作流由 `build_upload` 事件触发且 App Store Connect 已将某个构建与该上传关联时可用。`build_upload.state: complete` 表示上传已完成，而不是 App Store Connect 已完成构建处理。使用 `external_groups` 时，请先在 App Store Connect 中完成所需的 TestFlight 测试信息。

```yaml .eas/workflows/testflight-after-asc-upload.yml
name: Distribute to TestFlight after ASC upload

on:
  app_store_connect:
    build_upload:
      states:
        - complete

jobs:
  distribute_to_testflight:
    name: Distribute to TestFlight
    type: testflight
    params:
      asc_build_id: ${{ app_store_connect.build_upload.build.id }}
      internal_groups:
        - QA Team
      external_groups:
        - Public Beta
      changelog: Build from CI
      submit_beta_review: true
```

</Collapsible>

<Collapsible summary="在不重新提交 Beta App Review 的情况下更新更新日志">

对于已存在于 App Store Connect 中的构建，你可以更新“要测试的内容”说明或组成员关系，而无需触发 Beta App Review。将 `submit_beta_review: false` 设为在保留构建现有审核状态不变的同时应用这些更改。

此工作流将构建 ID 和新的更新日志作为 [手动输入](/eas/workflows/syntax/#onworkflow_dispatchinputs)，因此你可以使用 `eas workflow:run` 按需运行它。

```yaml .eas/workflows/testflight-update-changelog.yml
name: Update TestFlight changelog

on:
  workflow_dispatch:
    inputs:
      asc_build_id:
        type: string
        required: true
        description: 要更新的 App Store Connect 构建 ID。
      changelog:
        type: string
        required: true
        description: 新的“要测试的内容”说明。

jobs:
  update_changelog:
    name: Update changelog
    type: testflight
    params:
      asc_build_id: ${{ inputs.asc_build_id }}
      changelog: ${{ inputs.changelog }}
      submit_beta_review: false
```

</Collapsible>

## 更新

使用 [EAS Update](/eas-update/introduction/) 发布更新。

<Prerequisites>
  <Requirement title="已配置 EAS Update">
    要发布更新预览并推送空中更新。运行 `npx eas-cli@latest
    update:configure`，然后创建新构建。了解更多关于 [配置 EAS
    Update](/eas-update/getting-started/#prerequisites) 的信息。
  </Requirement>
</Prerequisites>

### 语法

```yaml
jobs:
  publish_update:
    type: update
    environment: production | preview | development # 可选，默认为 production
    env: # 可选的环境变量列表
      ENV_VAR_NAME: value
    params:
      message: string # 可选
      platform: string # 可选 - android | ios | all，默认为 all
      branch: string # 可选
      channel: string # 可选 - 不能与 branch 一起使用
      rollout_percentage: number # 可选 - 0 到 100，默认为 100
      private_key_path: string # 可选
      upload_sentry_sourcemaps: boolean # 可选 - 默认为“尝试上传，但上传失败时不使作业失败”
    hooks:
      after_checkout: step[] # 可选 - 作业检出项目后运行的步骤。
      before_install_node_modules: step[] # 可选 - 作业安装依赖前运行的步骤。
      after_install_node_modules: step[] # 可选 - 作业安装依赖后运行的步骤。
      before_update: step[] # 可选 - 发布更新前运行的步骤。
      after_update: step[] # 可选 - 发布更新后运行的步骤。
```

#### 环境变量

你可以通过 `env` 参数传入一个环境变量列表。这些环境变量将从 [EAS 环境变量](/eas/environment-variables/) 中提取。传入的 `environment` 参数将用于该环境变量的环境，这在同一个环境变量跨不同环境定义时很有用。

#### 参数

你可以将以下参数传入 `params` 列表：

| 参数                     | 类型    | 描述                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------ | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| message                  | string  | 可选。用于更新的消息。如果未提供，将使用提交信息。                                                                                                                                                                                                                                                                                                                                                                   |
| platform                 | string  | 可选。用于更新的平台。可以是 `android`、`ios` 或 `all`。默认为 `all`。                                                                                                                                                                                                                                                                                                                                                              |
| branch                   | string  | 可选。用于更新的分支。如果未提供，将使用工作流运行中的分支。对于手动运行的工作流，你需要提供一个值。例如：`${{ github.ref_name \|\| 'testing' }}`。请只提供 _分支_ 或 _频道_ 其中之一，不要同时提供。                                                                                                                                                                                          |
| channel                  | string  | 可选。用于更新的频道。请只提供 _分支_ 或 _频道_ 其中之一，不要同时提供。                                                                                                                                                                                                                                                                                                                                                                   |
| rollout_percentage       | number  | 可选。该更新应立即对多少比例的用户可用。必须是介于 `0` 和 `100` 之间的整数。这相当于向 EAS CLI 传递 `--rollout-percentage`。                                                                                                                                                                                                                                                                 |
| private_key_path         | string  | 可选。包含与 [EAS Update 配置](/eas-update/code-signing/#publish-a-signed-update-for-your-app) 中证书对应的 PEM 编码私钥的文件路径。你可以使用 `"$VARIABLE_NAME"` 语法引用文件类型的 [EAS 环境变量](/eas/environment-variables/)。这相当于向 EAS CLI 传递 `--private-key-path`。                                                                   |
| upload_sentry_sourcemaps | boolean | 可选。是否上传 Sentry sourcemaps。如果值为 `true`，作业将上传 Sentry source maps，并在上传失败时使作业失败。如果值为 `false`，作业不会将 sourcemaps 上传到 Sentry。如果未提供该值，作业将检查是否安装了 `@sentry/react-native`；如果已安装，则尝试上传 sourcemaps。如果失败，则只会打印错误信息，并继续执行，且作业仍标记为成功。 |

#### 输出

你可以在后续作业中引用以下输出：

| 输出                  | 类型   | 描述                                                   |
| --------------------- | ------ | ------------------------------------------------------------- |
| first_update_group_id | string | 第一个更新组的 ID。                             |
| updates_json          | string | 包含所有更新组信息的 JSON 字符串。 |

#### Hooks

Update 作业支持以下 hooks：

- `after_checkout`：作业检出项目后运行的步骤。
- `before_install_node_modules`：作业安装项目依赖前运行的步骤。
- `after_install_node_modules`：作业安装项目依赖后运行的步骤。
- `before_update`：发布更新前运行的步骤。
- `after_update`：发布更新后运行的步骤。Hook 步骤可以访问发布过程中生成的文件（例如 **dist** 目录中的 sourcemaps）。

有关通用 hooks 语法，请参阅 [`jobs.<job_id>.hooks`](/eas/workflows/syntax/#jobsjob_idhooks)。

### 示例

以下是一些使用 update 作业的实际示例：

<Collapsible summary="发布到生产频道的基础更新">

当你推送到 main 分支时，此工作流会使用提交信息作为更新消息，将更新发布到生产频道。

```yaml .eas/workflows/update-production.yml

  push:
```

```yaml .eas/workflows/update-platforms.yml

    name: Update Android
    type: update

      platform: android
      channel: production

    name: Update iOS
    type: update
    params:
      platform: ios
      channel: production
```

</Collapsible>

<Collapsible summary="基于分支部署的更新">

此工作流会根据分支名称发布更新，从而可以基于分支使用不同的环境（staging/production）。

```yaml .eas/workflows/update-branches.yml

  push:
    branches: ['main', 'staging']

      message: '分支更新：${{ github.ref_name }}'
```

</Collapsible>

<Collapsible summary="发布更新后上传 sourcemaps">

此工作流会发布更新，然后使用内置的 [`eas/posthog_upload_sourcemaps`](/eas/workflows/syntax/#easposthog_upload_sourcemaps) 函数将生成的 sourcemaps 上传到 PostHog。发布更新会在 **dist** 目录中生成 sourcemaps，该目录是此函数默认的上传目录。这些文件仅存在于运行作业的工作节点上，因此上传操作必须在 `after_update` hook 中执行，而不能放在单独的作业中。Hook 步骤会继承作业的环境，因此你可以将 `POSTHOG_CLI_API_KEY` 和 `POSTHOG_CLI_PROJECT_ID` 凭据作为 [EAS 环境变量](/eas/environment-variables/) 提供。要上传到其他服务，请改为在 `run` 步骤中运行该服务的上传命令。

```yaml .eas/workflows/update-with-sourcemaps.yml
name: Update with sourcemaps

on:
  push:
    branches: ['main']

jobs:
  update:
    name: Publish update
    type: update
    params:
      channel: production
    hooks:
      after_update:
        - uses: eas/posthog_upload_sourcemaps
```

</Collapsible>

## 更新发布

增加正在进行中的 [EAS 更新](/eas-update/introduction/)发布的比例。使用此功能可以逐步发布更新组，该更新组已通过部分 `rollout_percentage` 发布给一部分用户。

### 语法

```yaml
jobs:
  roll_out_update:
    type: update-rollout
    params:
      update_group_id: string # 必填
      rollout_percentage: number # 可选 - 0 到 100，默认为 100
```

#### 参数

你可以将以下参数传入 `params` 列表：

| 参数               | 类型   | 描述                                                                                                                                                                                                                                                       |
| ------------------ | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| update_group_id    | string | 必填。要更改发布比例的更新组 ID。通常，这是前置 [`update`](#update) 作业的 `first_update_group_id` 输出。该组必须有正在进行中的发布，否则作业将失败。                                   |
| rollout_percentage | number | 可选。此更新组应发布给的用户百分比。必须是介于 `0` 和 `100` 之间的整数，且不得低于该组当前的发布比例。默认为 `100`，这会将更新发布给所有用户并完成发布。 |

#### 输出

你可以在后续作业中引用以下输出：

| 输出               | 类型   | 描述                                                               |
| ------------------ | ------ | -------------------------------------------------------------------- |
| update_group_id    | string | 已完成发布的更新组 ID。                      |
| rollout_percentage | number | 应用于更新组的发布比例。         |
| updates_json       | string | 包含组中所有更新信息的 JSON 字符串。 |

### 示例

以下是使用更新发布作业的一些实际示例：

<Collapsible summary="发布部分更新，然后在批准后完成发布">

此工作流会将更新发布给 25% 的用户，等待批准，然后才将发布比例提升到 100%。

```yaml .eas/workflows/update-rollout.yml
name: 分阶段发布更新

on:
  push:
    branches: ['main']

jobs:
  publish_update:
    name: 将更新发布给 25% 的用户
    type: update
    params:
      channel: production
      rollout_percentage: 25

  require_approval:
    name: 发布给所有用户？
    type: require-approval
    needs: [publish_update]

  complete_rollout:
    name: 发布给所有用户
    type: update-rollout
    needs: [publish_update, require_approval]
    params:
      update_group_id: ${{ needs.publish_update.outputs.first_update_group_id }}
      rollout_percentage: 100
```

## 删除分支

在当前项目中删除一个 [EAS Update](/eas-update/introduction/) 分支。与 [`eas branch:delete`](/eas-update/eas-cli/#delete-a-branch) 相同。在 `branch_name` 中传入 EAS Update 分支名称。

### 语法

```yaml
jobs:
  delete_branch:
    type: branch-delete
    params:
      branch_name: string # 必填
      fail_on_missing: boolean # 可选，默认值：false
```

#### 参数

你可以将以下参数传入 `params` 列表：

| 参数            | 类型      | 描述                                                                                                                                                    |
| --------------- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| branch_name     | string    | 必填。要删除的 EAS Update 分支名称。                                                                                                                         |
| fail_on_missing | boolean   | 如果为 `false`，当分支不存在时，任务成功完成。如果为 `true`，当分支缺失时，任务会因校验错误而失败。默认值为 `false`。 |

#### 输出

你可以在后续任务中引用以下输出：

| 输出        | 类型   | 描述                                                                                       |
| ----------- | ------ | ------------------------------------------------------------------------------------------ |
| branch_id   | string | 已删除分支的 UUID；如果分支缺失且 `fail_on_missing` 为 `false`，则为 `null`。               |
| branch_name | string | 来自 `params.branch_name` 的分支名称。                                                     |

### 示例

参见 [清理更新分支示例](/eas/workflows/examples/branch-cleanup)，了解一个使用 [`on.ref_delete`](/eas/workflows/syntax/#onref_delete) 和 `branch-delete` 任务的工作流。

## Maestro

在 Android Emulator 或 iOS Simulator 构建上运行 Maestro 测试。

> **重要** Maestro 测试处于 [alpha](/more/release-statuses/#alpha) 阶段。

### 语法

```yaml
jobs:
  run_maestro_tests:
    type: maestro
    environment: 生产 | 预览 | 开发 # 可选 - 默认为预览
    image: string # 可选 - 可用镜像列表请参见 https://docs.expo.dev/build-reference/infrastructure/。
    runs_on: string # 可选 - 对于 Android Emulator 测试，请使用 linux-*-nested-virtualization worker。可用选项请参见 https://docs.expo.dev/eas/workflows/syntax/#jobsjob_idruns_on。
    params:
      build_id: string # 必需
      flow_path: string | string[] # 必需
      shards: number # 可选 - 默认为 1
      retries: number # 可选 - 默认为 0
      retry_failed_only: boolean # 可选 - 默认为 true
      record_screen: boolean # 可选 - 默认为 false
      include_tags: string | string[] # 可选
      exclude_tags: string | string[] # 可选
      maestro_version: string # 可选 - 默认为最新
      android_system_image_package: string # 可选
      device_identifier: string | { android?: string, ios?: string } # 可选
      output_format: string # 可选 - 默认为 junit
      skip_build_check: boolean # 可选 - 默认为 false
    hooks:
      after_checkout: step[] # 可选 - 作业检出项目后要运行的步骤。
      before_maestro_tests: step[] # 可选 - 测试开始前要运行的步骤。
      after_maestro_tests: step[] # 可选 - 测试完成后要运行的步骤。
```

#### 参数

你可以将以下参数传入 `params` 列表：

| 参数                         | 类型                                                  | 描述                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| build_id                     | string                                                | 必需。要测试的构建 ID。                                                                                                                                                                                                                                                                                                                                                                                                                |
| flow_path                    | string or string[]                                    | 必需。要运行的 Maestro flow 文件或目录的路径。                                                                                                                                                                                                                                                                                                                                                                                       |
| shards                       | number                                                | 可选且为实验性功能。将测试拆分为多少个分片。默认为 1。                                                                                                                                                                                                                                                                                                                                                                               |
| retries                      | number                                                | 可选。如果测试失败，重试的次数。默认为 0。                                                                                                                                                                                                                                                                                                                                                                                           |
| retry_failed_only            | boolean                                               | 可选。当为 true（默认）时，在适用情况下，重试将只重新运行上一次尝试中失败的 flows。设置为 false 可在每次重试时重新运行所有 flows。                                                                                                                                                                                                                                                                                               |
| record_screen                | boolean                                               | 可选。是否录制屏幕。默认为 false。注意：录制屏幕可能会影响模拟器性能。录制屏幕时你可能希望使用 large runners。                                                                                                                                                                                                                                                                                                                     |
| include_tags                 | string or string[]                                    | 可选。要包含在测试中的 flow 标签。会作为 `--include-tags` 传递给 Maestro。                                                                                                                                                                                                                                                                                                                                                          |
| exclude_tags                 | string or string[]                                    | 可选。要从测试中排除的 flow 标签。会作为 `--exclude-tags` 传递给 Maestro。                                                                                                                                                                                                                                                                                                                                                          |
| maestro_version              | string                                                | 可选。要用于测试的 Maestro 版本。如果未提供，将使用最新版本。                                                                                                                                                                                                                                                                                                                                                                      |
| output_format                | string                                                | 可选。Maestro 测试报告格式。默认为 `junit`。会作为 `--format` 传递给 Maestro。可以是 `junit` 或其他受支持的格式。                                                                                                                                                                                                                                                                                                                  |
| android_system_image_package | string                                                | 可选。要使用的 Android Emulator 系统镜像包。在你的机器上运行 `sdkmanager --list` 以列出可用包。请选择 `x86_64` 变体。示例：`system-images;android-36;google_apis;x86_64`、`system-images;android-35-ext15;google_apis_playstore;x86_64`。请注意，更高版本的镜像需要更多计算资源，因此你可能希望使用 large runners。                                                 |
| device_identifier            | string or `{ android?: string, ios?: string }` object | 可选。要用于测试的设备标识符。你也可以使用单值表达式，例如 `pixel_6`、`iPhone 16 Plus` 或 `${{ needs.build.outputs.platform == "android" ? "pixel_6" : "iPhone 16 Plus" }}`，以及对象形式，如 `device_identifier: { android: "pixel_6", ios: "iPhone 16 Plus" }`。请注意，iOS 设备在不同 runner 镜像上的可用性不同。可用设备列表可在作业日志中找到。 |
| skip_build_check             | boolean                                               | 可选。跳过构建校验（即 iOS 构建是否为模拟器构建）的验证。默认为 false。                                                                                                                                                                                                                                                                                                                                                              |

#### Hooks

Maestro 作业支持以下 hooks：

- `after_checkout`：作业检出项目后要运行的步骤。
- `before_maestro_tests`：测试开始前要运行的步骤。
- `after_maestro_tests`：测试完成后要运行的步骤。

有关通用 hooks 语法，请参见 [`jobs.<job_id>.hooks`](/eas/workflows/syntax/#jobsjob_idhooks)。

## GitHub 评论

自动将你的工作流已完成的构建、更新和部署报告发布到 GitHub 拉取请求中。它特别适用于为 PR 构建提供即时反馈、通过二维码共享测试构建以便轻松在设备上测试、展示 EAS Hosting 部署预览，以及自动化部署通知。你也可以通过提供 `payload` 参数来覆盖评论内容。

<Prerequisites>
  <Requirement title="与你的项目连接的 GitHub 仓库">
    要使用 GitHub Comment 作业，你的项目必须已连接一个 GitHub 仓库。了解如何
    [连接你的 GitHub 仓库](/build/building-from-github/) 以开始使用。
  </Requirement>
</Prerequisites>

### 语法

```yaml
jobs:
  github_comment:
    type: github-comment
    params:
      message: string # 可选 - 要包含在报告中的自定义消息
      build_ids: string[] # 可选 - 要包含的特定构建 ID，默认是与正在运行的工作流相关的全部构建
      update_group_ids: string[] # 可选 - 要包含的特定更新组 ID，默认是与工作流相关的全部更新
      deployment_ids: string[] # 可选 - 要包含的特定部署 ID，默认是与工作流相关的全部部署

  # 不使用 message 以及 builds、updates 和 deployments 表格的情况下，你也可以通过 `payload` 覆盖评论内容
  custom_github_comment:
    type: github-comment
    params:
      payload: string # 可选 - 用于完全自定义评论的原始 markdown/HTML 内容
```

#### 参数

该作业有两种互斥模式：

##### 模式 1：自动发现并可覆盖模式

默认行为是自动发现构建和更新，如果你愿意，也可以指定以下任意参数：

| 参数 | 类型 | 描述                                                                                                                                                      |
| ---- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| message | string | 可选。要包含在评论顶部的自定义消息。默认为 "你的构建、更新和部署已准备好进行测试！"                        |
| build_ids | string[] | 可选。要包含的特定构建 ID 数组。如果未指定，则自动发现所有已完成/失败/已取消的构建。使用空数组 `[]` 可排除构建。 |
| update_group_ids | string[] | 可选。要包含的特定更新组 ID 数组。如果未指定，则自动发现所有成功的更新。使用空数组 `[]` 可排除更新。       |
| deployment_ids | string[] | 可选。要包含的特定部署 ID 数组。如果未指定，则自动发现所有成功的部署。使用空数组 `[]` 可排除部署。 |

> **自动发现行为**：当未指定（即未定义）`build_ids`、`update_group_ids` 或 `deployment_ids` 时，作业会自动发现当前工作流中所有相关的构建、更新和部署。若要明确排除构建、更新或部署，请传入空数组 `[]`。

##### 模式 2：Payload 模式

使用 payload 模式时，不能指定任何其他参数。

| 参数 | 类型 | 描述                                                                                    |
| ---- | ------ | --------------------------------------------------------------------------------------- |
| payload | string | 作为评论发布的原始 markdown 或 HTML 内容。支持工作流变量插值。 |

#### 输出

你可以在后续作业中引用以下输出：

| 输出 | 类型 | 描述                                                                                |
| ---- | ---- | ----------------------------------------------------------------------------------- |
| comment_url | string | 已发布 GitHub 评论的 URL（仅在评论成功发布时可用）。 |

### 示例

## Apple 设备注册请求

Pause a workflow run until an iOS device enrolls for a specific [Apple team](https://expo.fyi/apple-team) and a team member approves that enrollment on [expo.dev](https://expo.dev). Use this job to automate registering a device for [internal distribution](/build/internal-distribution/) inside EAS Workflows.

当工作流到达此作业时，该作业和运行会进入 `action-required` 状态，并保持暂停，直到流程完成：

1. 工作流运行页面会显示该设备的二维码和注册链接。
2. 在 iPhone 或 iPad 上，设备会下载一个配置描述文件，并通过“设置”安装它。任一时刻只会有一个描述文件可用，如果未在八分钟内安装，它将被移除。
3. 安装后，会收集唯一设备标识符（UDID）和元数据。
4. 在工作流运行页面上，团队成员批准或拒绝该注册。批准会使作业成功，并将输出（UDID、型号等）暴露给下游作业。拒绝会使作业失败，并阻止使用 `needs` 的作业。

如果 UDID 已经在你的账户中注册，该作业在继续之前仍会等待注册和批准。

### 语法

```yaml
jobs:
  register_device:
    type: apple-device-registration-request
    params:
      apple_team_identifier: string # 可选
```

#### 参数

你可以将以下参数传入 `params` 列表：

| 参数 | 类型 | 描述 |
| --------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| apple_team_identifier | string | 可选。Apple Team ID（例如 `ABCDE12345`）。如果省略此参数，且你的 Expo 账户中只有一个 Apple team，则使用该团队。当你的账户中没有 Apple team 或有两个及以上 Apple team 时，必须设置此参数。提供该参数后，EAS 会根据该标识符解析或创建团队。 |

#### 输出

在团队成员批准已注册设备后，你可以在后续作业中引用以下输出：

| 输出 | 类型 | 描述 |
| ---------------- | ------ | ---------------------------------------------------------------- |
| apple_device_id  | string | Expo 内部设备 ID。                                         |
| identifier       | string | 设备 UDID。                                                     |
| name             | string | 设备名称。可能为空。                                       |
| model            | string | 硬件型号字符串（例如 `iPhone11,2`）。可能为空。 |
| device_class     | string | 设备类别：`iphone`、`ipad` 或 `mac`。可能为空。          |
| software_version | string | iOS 版本字符串。可能为空。                                |

如果团队成员拒绝该注册，作业会失败且不会设置输出。使用 `needs` 的下游作业将不会运行。

### 示例

以下是一些使用 Apple 设备注册请求作业的实际示例：

```yaml .eas/workflows/register-device-slack.yml

    params:
      webhook_url: ${{ env.SLACK_WEBHOOK_URL }}
      message: 'Registered device ${{ needs.register_device.outputs.identifier }} (${{ needs.register_device.outputs.model }})'
```

## 重打包

基于现有构建对应用进行重新打包。此任务会重新打包应用的元数据和 JavaScript bundle，而不执行完整的原生重建，这对于创建与特定指纹兼容、速度更快的构建非常有用。

```yaml
jobs:

    type: repack
    runs_on: string # 可选 - 可用选项请参见 https://docs.expo.dev/build-reference/infrastructure/
    params:
      build_id: string # required
      profile: string # optional
      embed_bundle_assets: boolean # optional
      js_bundle_only: boolean # optional
      ios_signing_use_source_app_entitlements: boolean # optional
      ios_signing_app_entitlements_path: string # optional
      message: string # optional
      repack_version: string # optional
      repack_package: string # optional
    hooks:
      after_checkout: step[] # optional - steps to run after the job checks out your project.
      before_install_node_modules: step[] # optional - steps to run before the job installs dependencies.
      after_install_node_modules: step[] # optional - steps to run after the job installs dependencies.
```

> **注意：** 如果构建可能仍在进行中，请使用 [`get-build`](#get-build) 并设置 `wait_for_in_progress: true`，然后将其 `build_id` 传递给 `repack`。

### 常见问题

<FAQ>

<Collapsible summary="何时使用重打包，何时不使用？">

重打包任务适用于以下场景：

- 通过复用现有构建来减少 CI 构建时间
- 在需要时触发完整的原生构建
- 为团队提供更快的反馈循环

重打包任务不适用于以下场景：

- 需要完整流程才能正确完成符号化和应用签名的生产构建

#### 参数

你可以向 `params` 列表传入以下参数：

| 参数                                      | 类型    | 描述                                                                                                                                                                                                          |
| ----------------------------------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| build_id                                  | string  | 必需。要重新打包的构建的源构建 ID。                                                                                                                                                                            |
| profile                                   | string  | 可选。要使用的构建配置文件。默认使用从 `build_id` 检索到的源构建配置文件。                                                                                                                                    |
| embed_bundle_assets                       | boolean | 可选。是否将 bundle 资源嵌入到重新打包的构建中。默认会根据源构建自动确定。                                                                                                                                    |
| js_bundle_only                            | boolean | 可选。是否仅重新打包 JavaScript bundle。默认值为 false，表示将更新整个应用元数据。                                                                                                                          |
| message                                   | string  | 可选。附加到构建上的自定义消息。对应于运行 `eas build` 时的 `--message` 标志。                                                                                                                               |
| repack_version                            | string  | 可选。要使用的 `@expo/repack-app` 版本。默认使用最新版本。                                                                                                                                                    |
| repack_package                            | string  | 可选。要使用的 repack npm 包。默认值为 `@expo/repack-app`。                                                                                                                                                   |
| ios_signing_use_source_app_entitlements   | boolean | 可选。是否使用 fastlane resign 的 `use_app_entitlements` 行为：提取应用包代码签名 entitlements，并将其与新配置文件中的 entitlements 组合。默认值为 false。                                                 |
| ios_signing_app_entitlements_path         | string  | 可选。要使用的 entitlements 文件路径，例如 `myApp/MyApp.entitlements`。此项与 `ios_signing_use_source_app_entitlements` 互斥。                                                                                  |

#### Hooks

Repack 任务支持以下 hooks：

- `after_checkout`：任务检出项目后要运行的步骤。
- `before_install_node_modules`：任务安装项目依赖前要运行的步骤。
- `after_install_node_modules`：任务安装项目依赖后要运行的步骤。

有关通用 hooks 语法，请参阅 [`jobs.<job_id>.hooks`](/eas/workflows/syntax/#jobsjob_idhooks)。

### 示例

以下是一些在重打包任务中使用指纹的实际示例：

<Collapsible summary="使用 Fingerprint 和 Repack 进行持续部署">

此工作流首先生成指纹，然后根据该指纹是否已存在兼容构建来决定是构建还是重打包应用。最后，它运行 Maestro 测试。

```yaml .eas/workflows/cd-fingerprint-repack.yml
name: continuous-deploy-fingerprint

jobs:
  fingerprint:
    id: fingerprint
    type: fingerprint
    # @info 与你的构建配置文件环境匹配 #
    environment: production
    # @end #

  android_get_build:
    needs: [fingerprint]
    id: android_get_build
    type: get-build
    params:
      fingerprint_hash: ${{ needs.fingerprint.outputs.android_fingerprint_hash }}
      platform: android

  android_repack:
    needs: [android_get_build]
    id: android_repack
    if: ${{ needs.android_get_build.outputs.build_id }}
    type: repack
    params:
      build_id: ${{ needs.android_get_build.outputs.build_id }}

  android_build:
    needs: [android_get_build]
    id: android_build
    if: ${{ !needs.android_get_build.outputs.build_id }}
    type: build
    params:
      platform: android
      profile: preview-simulator

  android_maestro:
    after: [android_repack, android_build]
    id: android_maestro
    type: maestro
    image: latest
    params:
      build_id: ${{ needs.android_repack.outputs.build_id || needs.android_build.outputs.build_id }}
      flow_path: ['maestro.yaml']

  ios_get_build:
    needs: [fingerprint]
    id: ios_get_build
    type: get-build
    params:
      fingerprint_hash: ${{ needs.fingerprint.outputs.ios_fingerprint_hash }}
      platform: ios

  ios_repack:
    needs: [ios_get_build]
    id: ios_repack
    if: ${{ needs.ios_get_build.outputs.build_id }}
    type: repack
    params:
      build_id: ${{ needs.ios_get_build.outputs.build_id }}

  ios_build:
    needs: [ios_get_build]
    id: ios_build
    if: ${{ !needs.ios_get_build.outputs.build_id }}
    type: build
    params:
      platform: ios
      profile: preview-simulator

  ios_maestro:
    after: [ios_repack, ios_build]
    id: ios_maestro
    type: maestro
    image: latest
    params:
      build_id: ${{ needs.ios_repack.outputs.build_id || needs.ios_build.outputs.build_id }}
      flow_path: ['maestro.yaml']
```
