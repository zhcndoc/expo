`expo-updates` 是一个让你的应用能够管理应用代码远程更新的库。它会与配置的远程更新服务通信，以获取可用更新的信息

## 安装

`expo-updates` 库可以使用 [EAS Update](/eas-update/introduction/) 自动配置。EAS Update 是一个托管服务，用于管理并向你的应用提供更新。要开始使用 EAS Update，请按照 [开始使用](/eas-update/getting-started/)指南中的说明操作

此外，在需要使用其他远程更新服务，或仅在原生文件中指定配置的情况下，也可以手动配置 `expo-updates` 库

<Collapsible summary="手动安装、配置和自定义远程更新服务">

<APIInstallSection hideBareInstructions />

如果你是在[现有的 React Native 项目](/bare/overview/)或手动配置原生代码的通用应用中安装此库，请遵循这些[安装说明](/bare/installing-updates/)

如果使用[应用配置](/workflow/configuration/)进行配置，则可以通过至少设置以下应用配置属性来配置此库：

- [`updates.url`](../config/app/#updates)：实现 [Expo Updates 协议](/technical-specs/expo-updates-1/)的远程服务 URL
- [`runtimeVersion`](../config/app/#runtimeversion)：一个[运行时版本](#运行时版本)

远程服务必须实现 [Expo Updates 协议](/technical-specs/expo-updates-1/)。[EAS Update](/eas-update/introduction) 就是此类服务之一，但也可以将此库与自定义服务器一起使用

两个核心必需配置选项是：

- [`updates.url`](../config/app/#updates)：该库获取远程更新的 URL
- [`runtimeVersion`](../config/app/#runtimeversion)：一个[运行时版本](#运行时版本)

按照 EAS Update [开始使用](/eas-update/getting-started/)指南操作时，这些配置会自动完成

### 运行时版本

每次为应用构建二进制文件时，其中都会包含构建时存在的原生代码和配置，以及原生配置；这些内容的唯一组合由一个称为运行时版本的字符串表示。远程更新会针对一个运行时版本，这表示只有具有匹配运行时版本的二进制文件才能加载该远程更新

<Collapsible summary="手动配置">

可以通过在配置字段中设置字符串值来手动管理运行时版本

```json
{
  "expo": {
    "runtimeVersion": "<runtime_version_string>"
  }
}
```

</Collapsible>

<Collapsible summary = "使用运行时版本策略自动配置">

运行时版本策略会根据项目中已有的其他信息推导运行时版本。可以按如下方式在 [`runtimeVersion`](../config/app/#runtimeversion) 配置字段中设置：

```json
{
  "expo": {
    "runtimeVersion": {
      "policy": "<policy_name>"
    }
  }
}
```

可用的策略类型：

<Collapsible summary="appVersion">

`"appVersion"` 策略适用于希望根据应用版本定义运行时兼容性的项目

例如，某个项目的应用配置如下：

```json
{
  "expo": {
    "runtimeVersion": {
      "policy": "appVersion"
    },
    "version": "1.0.0",
    "ios": {
      "buildNumber": "1"
    },
    "android": {
      "versionCode": 1
    }
  }
}
```

`"appVersion"` 策略会将运行时版本设置为项目当前的 `"version"` 属性。在此示例中，Android 和 iOS 构建以及任何更新的运行时版本都会是 `"1.0.0"`

对于包含自定义原生代码，并在每次公开发布后更新 `"version"` 字段的项目，此策略非常适用。要提交应用，应用商店要求每个提交的构建都具有更新后的原生版本号，因此如果你希望确保用户设备上安装的每个版本都有不同的运行时版本，此策略会很方便

使用此策略时，每次公开发布时都需要手动更新应用配置中的 `"version"` 字段，但对于 Play Store 的 Internal Test Track 和 App Store 的 TestFlight 上传，可以依靠 **eas.json** 中的 `"autoIncrement"` 选项来[为你管理版本](/build-reference/app-versions/#remote-version-source)

</Collapsible>

<Collapsible summary="nativeVersion">

`"nativeVersion"` 策略适用于希望根据项目当前的 `"version"` 和 `"versionCode"`（Android）或 `"buildNumber"`（iOS）属性定义运行时兼容性的项目

例如，某个项目的应用配置如下：

```json
{
  "expo": {
    "runtimeVersion": {
      "policy": "nativeVersion"
    },
    "version": "1.0.0",
    "ios": {
      "buildNumber": "1"
    },
    "android": {
      "versionCode": 1
    }
  }
}
```

Android 和 iOS 构建以及任何更新的运行时版本都会是 `"[version]([buildNumber|versionCode])"` 的组合，在此示例中即为 `"1.0.0(1)"`

对于包含自定义原生代码，并在每次构建时更新原生版本号（iOS 的 `"buildNumber"` 和 Android 的 `"versionCode"`）的项目，此策略非常适用。要提交应用，应用商店要求每个提交的构建都具有更新后的原生版本号，因此如果你希望确保上传到 Play Store 的 Internal Test Track 和 App Store 的 TestFlight 分发工具的每个应用都有不同的 `runtimeVersion`，此策略会很方便

需要注意的是，此策略要求在每次构建之间手动管理原生版本号

此外，如果你在 Android 和 iOS 之间选择不同的原生版本，最终构建和更新会具有各自独立的运行时版本

</Collapsible>

<Collapsible summary="fingerprint">

`"fingerprint"` 运行时版本策略会自动为你计算运行时版本，包括 SDK 升级或添加自定义原生代码等更改

```json
{
  "expo": {
    "runtimeVersion": {
      "policy": "fingerprint"
    }
  }
}
```

此策略适用于包含和不包含自定义原生代码的项目。它通过使用 [`@expo/fingerprint`](fingerprint) 包，在构建和更新期间计算项目的哈希值，以确定构建与更新的兼容性（也称为运行时）

</Collapsible>

</Collapsible>

### 原生配置和覆盖

如果你的项目不使用 Continuous Native Generation，也可以在应用的原生配置文件中设置这些配置值，或在原生代码初始化期间覆盖这些值

<Collapsible summary="原生配置说明">

在 Android 上，这些选项作为 `meta-data` 标签设置在 **AndroidManifest.xml** 文件中（如果使用自动设置，则与安装期间添加的标签相邻）。你也可以使用 `UpdatesController.overrideConfiguration()` 在运行时设置或覆盖这些选项

在 iOS 上，这些属性作为键设置在 **Expo.plist** 文件中。你也可以通过调用 `AppController.overrideConfiguration` 在运行时设置或覆盖这些属性

<Collapsible summary="导入 Swift 生成的标头以在 Objective-C++ 中使用">

如果你的 iOS 原生代码或 `AppDelegate.mm` 使用 Objective-C++ 编写，则需要添加以下导入，以引用 `EXUpdatesAppController` 上的方法。这仅在运行时覆盖配置时需要

```objc
#import "ExpoModulesCore-Swift.h"
#import "EXUpdatesInterface-Swift.h"
#import "EXUpdates-Swift.h"
```

</Collapsible>

## 使用

默认情况下，`expo-updates` 会在应用启动时检查更新。如果有可用更新，它会下载该更新，并在应用下次重启时应用更新。你可以使用上面的 `checkAutomatically` 和 `fallbackToCacheTimeout` 配置选项调整此启动行为

该库还提供了各种常量，用于检查当前更新，并提供函数让你从应用代码中（启动后）自定义更新行为。例如，一种常见的替代使用模式是在应用启动后手动检查更新，而不是执行默认的启动时检查

<Collapsible summary="示例：手动检查更新">

你可以通过以下步骤将应用配置为手动检查更新：

1. 将 `checkAutomatically` 配置值设置为 `ON_ERROR_RECOVERY` 或 `NEVER`，以禁用该库的默认启动行为
2. 添加以下代码来检查可用更新、下载更新并重新加载：

   ```jsx App.js
   import { View, Button } from 'react-native';
   import * as Updates from 'expo-updates';

   function App() {
     async function onFetchUpdateAsync() {
       try {
         const update = await Updates.checkForUpdateAsync();

         if (update.isAvailable) {
           await Updates.fetchUpdateAsync();
           await Updates.reloadAsync();
         }
       } catch (error) {
         // You can also add an alert() to see the error message in case of an error when fetching updates.
         alert(`Error fetching latest Expo update: ${error}`);
       }
     }

     return (
       <View>
         <Button title="Fetch update" onPress={onFetchUpdateAsync} />
       </View>
     );
   }
   ```

</Collapsible>

## 测试

此库中的大多数方法和常量只能在发布版本中使用或测试。在调试版本中，默认行为是始终从开发服务器加载最新的 JavaScript。你可以[构建一个具有与发布版本相同更新行为的调试版本应用](/eas-update/debug/#debugging-of-native-code-while-loading-the-app-through-expo-updates)。此类应用不会从开发服务器打开最新的 JavaScript，而是像发布版本一样加载已发布的更新。当应用未连接到开发服务器时，这可能有助于调试应用的行为

**要在开发版本中测试更新的内容**，请运行 [`eas update`](/eas-update/getting-started/)，然后在开发版本中浏览到该更新。请注意，这只能模拟更新在应用中的表现，并且大多数 [Updates API](#api) 在开发版本中运行时不可用

**要在发布版本中测试更新**，你可以创建一个 [**.apk**](/build-reference/apk) 或[模拟器构建版本](/build-reference/simulators)，也可以使用 `npx expo run:android --variant release` 和 `npx expo run:ios --configuration Release` 在本地创建发布版本（无需将此构建提交到商店即可进行测试）。完整的 [Updates API](#api) 在发布版本中可用

**要在 Expo Go 中测试更新的内容**，请运行 [`eas update`](/eas-update/getting-started/)，然后在 Expo Go 中浏览到该更新。请注意，这只能模拟更新在应用中的表现，并且大多数 [Updates API](#api) 在 Expo Go 中运行时不可用。另请注意，仅支持使用与 [Expo Go 兼容的库](/workflow/using-libraries/#determining-third-party-library-compatibility)的更新
