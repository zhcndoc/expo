## 在预览构建中预览更新

非技术用户通常不希望与开发构建交互，他们会希望在 [应用商店测试轨道](/review/overview/#app-store-testing-tracks) 或 [内部分发](/review/overview/#internal-distribution-with-eas-build) 中，通过预览构建来测试更改。

如果你的团队规模较小，通常一次向应用商店测试轨道或内部分发部署一个预览构建就足够了。然后，你可以将更新发布到该预览构建所使用的通道。[了解有关预览构建的更多信息](/review/overview/)。

另外，你可以在预览构建中内置一种机制，让用户选择要加载的其他更新或通道。当 [应用运行时](/eas-update/runtime-versions/) 不经常变更，并且同一个应用中可以加载许多不同更新时，这会很有用。[了解有关通道切换的更多信息](/eas-update/channel-surfing/)。

## 在生产构建中预览更新

在向所有最终用户部署更新之前，一些团队会希望先将其在生产环境中向一小部分内部用户进行发布。一种实现方式是针对已知的一部分用户使用 [频道切换](/eas-update/channel-surfing/)。仅对能够报告并从预览更新问题中恢复的用户使用这种方法，因为损坏的更新可能会阻止他们到达用于清除频道覆盖的界面。

另一种方法是使用类似于[持久化暂存流程](/eas-update/deployment-patterns/#persistent-staging-flow)的部署模式，该模式始终保留一个指向暂存频道的生产应用版本。
